# Experiment E0.2 — Repository verification

## Objective

Determine whether the repository as checked out on branch `desafio` is internally
consistent: every checksum manifest verifies, both split WIMs reassemble to the
documented SHA-256, the reassembled images carry the drivers the notes claim, and
the target DriverStore state matches the recorded layout.

## Fidelity level

`metadata only`. No Windows boot, no driver load, no QEMU, no hardware. Only file
bytes, WIM metadata, and INF declarations were read.

## Preconditions

- Branch `desafio` checked out, work tree clean before the run.
- The tracked WIM parts under `winre-1809-254MB/` and `winre-fabrica-10586-424MB/`
  are present and unmodified.
- Free space for a temporary reassembly of approximately 711 MB.
- No tracked file is written. Reassembly happens in `mktemp -d`.

## Environment

- Date: 2026-11-14
- Host: Linux container, Ubuntu 24.04.4 LTS
- Kernel: 5.10.134-18.0.13.lifsea8.x86_64
- Virtualization: no `/dev/kvm`; no VM booted in this experiment
- CPU: 2 vCPU, Memory: 4.0 GiB, free disk 22 GB
- Tools present: `7-Zip 23.01 (x64)`, `sha256sum`, `git`
- Tools absent: `wimlib-imagex`, `qemu-system-x86_64`, `xorriso`
- Repository: branch `desafio`, `HEAD` = `a0622af`

## Interpretation

### Observed facts

- All five `SHA256SUMS` manifests verify: 66 entries total.
- Both WIMs reassemble to exactly the documented SHA-256 values. The tracked parts
  are intact and in the correct order.
- The WIM **file** is larger than the WIM-level `TOTALBYTES` header field:

  | Image | File bytes | Header `TOTALBYTES` | Difference |
  |---|---:|---:|---:|
  | 10586 | 444,858,791 | 444,856,529 | +2,262 |
  | 1809 | 266,283,250 | 266,281,208 | +2,042 |

  `ANOTACOES-IMPORTANTES.md` (lines 18 and 42) and the E0.1 artifact table quote the
  header value as the image size. The values are the WIM metadata field, not the file
  size. Both hashes in those documents are correct and reproduce.
- `FileRepository` entries directly under the folder: 751 (10586) and 895 (1809).
  Adding the `FileRepository` node itself gives 752 and 896, matching the counts
  recorded in the notes and in E0.1. The documented metric is therefore "nodes in
  the tree including the top node".
- The 10586 image contains `bcmdhd.inf`, `bcmdhd64.inf`, `bcmfn.inf`, `bcmfn2.inf`,
  no `bcmwdidhdpcie.inf`, and no nvram file.
- The 1809 image contains `bcmwdidhdpcie.inf_amd64_977dcc915465b0e9` with the four
  target files.
- The 2017 INF is UTF-16LE; the OEM INF is ANSI. Both declare the versions the notes
  claim, both cover `DEV_43EC`, and only the OEM INF references the board nvram.
- Toolchain gap: `wimlib-imagex`, `qemu-system-x86_64`, and `xorriso` are not
  installed, and there is no `/dev/kvm`. Milestones M1 and M2 cannot run here yet.

### Hypotheses

- The 2 KB difference is WIM padding or a trailing region not counted by the
  `TOTALBYTES` field. Not investigated; it does not affect any hash.
- The E0.1 "Size" column was filled from `wimlib-imagex info`, whose `Size` line
  echoes the header field rather than `stat` of the file. That explains the
  discrepancy without implying a corrupted image.

## Decision

- Result: pass, for the repository half of M0.
- Reason: all checksums verify, both images reproduce their documented hashes, the
  driver layout and INF declarations match the notes, and the verifier detects
  injected faults (negative control failed as expected).
- Not covered: M0 also requires the tool inventory, which is now recorded here, but
  the missing WIM and QEMU tooling blocks M1 and M2.
- Next experiment: E0.1 remains blocked on an official 1809 reference for
  provenance. Installing `wimlib-imagex` and QEMU is a precondition for E1.

## Limitations

- `7z` reads WIM files; it is not a servicing tool. No package staging was tested.
- No QEMU boot was attempted. Nothing here proves driver installation behaviour.
- The BCM4356 radio is not emulated and was not touched.
- File hashes prove content equality, not provenance.

## Rollback

- No tracked WIM was modified; reassembly used `mktemp -d` and was removed on exit.
- The verifier rewrote only `scripts/verify-repo.sh` during the negative control and
  was restored from a backup copy; the restored run returned `77 passed, 0 failed`.
- `git status` after the run: `scripts/` and `setup.sh` untracked, no tracked file
  modified.
